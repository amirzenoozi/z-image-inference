# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Z-Image-Inference runs image generation models locally on Apple Silicon, with a React UI. All Python code is in `backend/` (tests in `backend/tests/`), the UI in `frontend/`; the data (`models/`, `history.db`, `.env` and the editable JSON files) stays at the project root, found through `backend/paths.py`. It is two processes:

- **`model_server.py`** (port 8000): loads one model at a time and generates images. All model work runs on one thread (`model_thread`), because MLX only works on the thread that created it.
- **`main.py`** (port 7860): FastAPI web app. Serves the built UI from `frontend/dist` and the `/api/*` endpoints (catalog, generate, history, chat, model status), and keeps history in `history.db`.

## Commands

```bash
uv sync                                          # Python dependencies
cd frontend && npm ci && npm run build           # build the UI (needed before main.py serves it)
uv run python backend/model_server.py            # model server
uv run python backend/main.py                    # web app at http://127.0.0.1:7860
cd frontend && npm run dev                       # UI with live reload; proxies /api to main.py

uv run pytest                                    # backend tests
cd frontend && npm test                          # frontend tests (Vitest)
cd frontend && npx tsc -b && npx oxlint src      # type-check and lint
make render FILE=list.json [DRY_RUN=1]           # render a list of JSON prompts through the running app
```

The `Makefile` wraps these one to one (`make help` lists the targets): `make setup` (runs `scripts/setup.sh`: checks Apple Silicon, Homebrew, git, uv and Node.js 20+, installs gitleaks, turns on the git hooks, creates `.env` once, then `uv sync` and the UI build; safe to rerun), `make build`, `make model-server`, `make app`, `make dev`, `make test`, `make lint`, `make check` (lint and tests, before a PR), and `make render` (below). Keep it a thin wrapper: a target is one of the commands above, with no logic of its own.

## Models

Defined once in `model_catalog.py` (shared by the UI and the server); loaders and downloads live in `model_server.py`. Files go in `models/` (not in git).

By default the original files are kept and run; `MODEL_COMPRESSION=on` in `.env` switches to the compressed copies below (`compression_enabled()` in `model_catalog.py`). Z-Image-Turbo is the exception: `Z_IMAGE_BITS` (`z_image_bits()`, default 8; 6, 5, 4, 3 or `original`) picks the quantised copy it runs, built into `models/zimage-q<bits>/` beside the original, which is always kept.

| Model | Engine | Compressed (`MODEL_COMPRESSION=on`) |
|-------|--------|-----------|
| Z-Image-Turbo (default) | mflux (MLX), 8-bit by default | Not affected; set by `Z_IMAGE_BITS` |
| WAI-NSFW-Illustrious v12 (SDXL) | diffusers on MPS, float16; VAE decodes in float32 | `models/waiNSFWIllustrious_v120/`, rewritten from float32 to float16 once |
| Anime Desire (Illustrious SDXL) | diffusers on MPS, float16, single-file checkpoint loaded with the SDXL configs in `models/sdxl-base-config/` | `models/anime-desire-illustrious/` |
| RealVisXL V5.0 (SDXL, photorealistic) | diffusers on MPS, float16 (only the fp16 files are downloaded), DPM++ 2M SDE Karras; the photo-style face lock | Not affected; already float16 |
| FLUX.1-dev (gated; needs `HF_TOKEN`); add-ons create-nsfw and asian-nudity-2 | mflux, always the 4-bit copy in `models/flux-dev-q4/` | Not affected; always 4-bit |
| MOSS-Image NSFW | diffusers on MPS, bfloat16; pipeline vendored in `moss_pipeline.py` | `models/moss-image-nsfw/`; text encoder kept 8-bit (optimum-quanto) in `text_encoder-q8/` |

- Only the default model downloads at start; the user downloads (`POST /models/{id}/download`, checked for free space) and removes (`DELETE /models/{id}`, files listed in `MODEL_FOLDERS`) the others from the model dialog. Downloads run one at a time in the background (`download_thread`) and finish with a `.download-complete` marker; `/generate` answers 503 with a message while a model downloads, and `/models/status` reports progress.
- One-time builds (Z-Image levels, FLUX.1-dev 4-bit, float16, 8-bit) write to a `.building` folder and rename it when complete (`build_once`).
- An add-on is ready only with its base model downloaded, its download fetches the base when missing, and removing it deletes only its LoRA (`lora-<id>/`). Models that became add-ons are listed in `MODELS_NOW_ADDONS`, and History moves their images to the base model with that add-on on start. `download_problem` refuses a FLUX.1-dev download without a Hugging Face token, and a Civitai one (`source="civitai"`, fetched from `download_url` by `download_from_civitai`) without `CIVITAI_TOKEN`. The model card links to `page_url` on its site.
- Add-ons (`AddonSpec`, `ADDONS` in `model_catalog.py`: tattoo for Z-Image-Turbo, create-nsfw and asian-nudity-2 for FLUX.1-dev) are LoRAs the user switches on over a base model, not models. The rule, the same for every add-on: a switched-on add-on is used only when the prompt mentions one of its `keywords` (whole words, any case), and then its trigger phrase is added if missing (`applied_addons`, `with_trigger_words`); switched off, or not mentioned, the base model renders alone. The model server applies it per render and loads the base with exactly those add-ons (`use_model`, reloading only when the set changes), and History records them (`addons`). They download and remove like models (`ENTRIES` in `model_server.py`). In the UI, the model dialog's Add-ons tab lists the selected model's add-ons with their details and downloads (`AddonCards`), and Create shows only a checkbox for each downloaded one (`AddonsPanel`). Add a new LoRA as an add-on, not as a model.
- Add-ons have a `kind` (`AddonKind`): `optional` (the checkbox rule above), `automatic` (no checkbox; used whenever the prompt mentions a keyword and it is downloaded, at its `scale`), and `slider` (a strength the request sends in `strengths`, checked against its `SliderRange`; 0 leaves it out). The model server loads each LoRA at a marker strength (`LORA_MARKER`), finds its layers (`lora_layers`) and sets each render's strengths before generating (`set_lora_strengths`), so a strength change needs no reload; only a change in the set reloads. In the UI, one slider (`shared/lookSliders/LookSliderField`) is used in Create's **Look** section (`LookSliders`, typed prompts only), the builder's Face & hair, Body and Character steps, and the character dialog, fed the downloaded sliders by `LookSlidersContext`. The rule is in `lib/lookSliders/`: a slider with a matching builder choice is linked both ways (`withStrength` picks the nearest option, `lookStrength` follows a picked one), the others add a phrase through `resolveFacts` (`lookPhrases`); builder state and character traits keep the strengths (`strengths`), the JSON prompt in `look`, and History in `strengths`.
- A/B test (`lib/abTest/`, run by `App/useAbTest`): 2 to 6 images (versions) on one seed, comparing 1 to 3 settings at once (look sliders and single-choice builder fields, mixed), each version a value for every setting. Each version's settings come from `testVersions` (a slider follows the linked-choice rule; a choice is set in the JSON prompt), and each image is saved with a set id and label (`set_id`, `set_label` in History, `GET /api/history/sets/{set_id}`), shown together in `shared/images/CompareDialog`. While a test runs, `AbTestContext` turns off what it locks (`lockedBuilderFields`: the model, the character, purpose, Who, Age, the tested field, the seed, Random, Surprise me, prompt replacement); a new control that could change those must read it too.
- Variations (image-to-image): the web app loads the start image from History and sends it with `change` (0.1–0.9). Z-Image passes it to mflux as `image_strength = 1 − change`; the SDXL models use an img2img pipeline built from the loaded parts, with the start image encoded in float32 (`encode_in_float32`). MOSS-Image cannot (`supports_variations=False`).
- Face lock (IP-Adapter plus-face, `models/ip-adapter/`, downloaded on first use by `face_lock_problem`): the SDXL models only (`supports_face_lock`). The web app loads the character's face image (`face_id`) and sends it as `face_image` with `face_strength`; the browser can't send one. `SdxlPipes` loads the adapter for face-locked renders and unloads it for the others, since diffusers needs a face image for every render while it is loaded.
- MOSS-Image's text encoder and image model do not fit in memory together, so they take turns; the last prompt's embeddings are cached.

## Code layout

- `generation_request.py`: request model and checks, shared by the web app and the model server.
- `resolutions.py`: resolution presets with category (square, portrait, landscape, widescreen) and size tier.
- `example_prompts.json`: each model's example prompts, keyed by model id and read on every catalog request. Keep every person in them clearly adult.
- `custom_clothes.json`: the user's own clothes (value, title per language, prompt, tags, slot, covers, group, for, adult), read on every catalog request by `custom_clothes.py`, which leaves out a broken entry with a problem; the browser checks it against the built-in options and the age safeguard (`lib/customClothes/`) and offers it through `lib/promptBuilder/customClothes/` wherever built-in garments are offered. An adult item is lingerie (the `lingerieTop`/`lingerieBottom` fields).
- `prompt_modes.json`: the prompt builder's purposes (content level, focus wording, steps, defaults, narrowed options, emphasis, tag weights), served in the catalog. What each content level allows (`safe`: no nudity or lingerie, safe negatives; `suggestive`: up to topless, no explicit poses or acts) is enforced in code (`rules/`, `negatives/`, `resolveFacts/`), not in the file. `main.py` checks the shape; `promptBuilder/modes/` (`parseModes`) checks steps and options against the builder and leaves out a mode it cannot use.
- `history_store.py`: SQLite history; images are stored in the database as lossless WebP (`image_codec.py`, pixel-checked, PNG kept when WebP is not smaller or the image is deeper than 8 bits), and rows saved before that as PNG, told apart by their first bytes. `image_png` always hands out PNG; `/api/history/{id}/image` sends the stored bytes, `/download` a PNG. `backend/tools/recompress_history.py` converts the older PNG rows, after a backup.
- `character_store.py`: characters (a name, the builder's identity choices, an optional cover and seed), in the same database; images link to one with `character_id`. Generate puts the chosen character's look in front of a typed prompt (`promptToSend` in `lib/characterPrompt/`, written by `characterLook`), unless `settings.lookIncluded` says the prompt already has it (builder prompts and reused images). The UI shares them through `CharactersProvider` / `useCharacters`, and `promptBuilder/character/` turns them into builder choices. A character must be an adult (`characterProblem`). `sample_characters.json` holds the samples `add_samples_once` adds once per database on startup (recorded in the `app_state` table); keep them clearly adult and limited to the builder's options, which `character/index.test.ts` checks.
- `frontend/src/`: React + TypeScript + Tailwind v4. `lib/` holds logic (settings, API client, prompt builder). The UI is split by where it is used: `pages/create/`, `pages/history/` and `pages/characters/` hold each page (`CreatePage`, `HistoryPage`, `CharactersPage`) and the components only it uses; `shared/` holds what more than one page uses, by topic (`ui/` for dialogs, buttons and the like, `form/`, `images/`, `characters/`, `promptBuilder/`). A component moves to `shared/` once a second page needs it. Every module and component has its own folder named after it, holding `index.ts(x)` and its test `index.test.ts(x)` (`lib/settings/index.ts`, `pages/create/PromptEditor/...`); a component used by only one other component sits in that component's `components/` folder (`pages/history/HistoryPage/components/HistoryViewer/`), and a hook used by only one module sits beside it in the same folder. The prompt builder stays together in `shared/promptBuilder/`, since two pages use it. Import a module by its folder (`../settings`), never `.../index`.
- `frontend/src/lib/promptBuilder/fitness/`: the Fitness purpose's workouts (with full descriptions), places, light, photo styles and clothing; `outfitOptions` is the one list each outfit slot offers a subject (spicy cuts only for a chosen adult, each item for who it suits), read by the Outfit step, Random, Surprise me and the prompt. Fitness stays safe for work: spicy means clothed.
- `frontend/src/lib/promptBuilder/intimates/` and `faceless/`: the Lingerie and Swimwear items of the Outfit step's Top and Bottom menus (`outfitMenu/` puts clothes, gym wear, lingerie and swimwear in one menu per area, one item at a time, while the state keeps `top`/`bottom` apart from `lingerieTop`/`lingerieBottom`; `intimateOptions`: each for who it suits, see-through ones only where the purpose can choose nudity), every item's full wording (`GARMENT_DETAILS`, used in sentence prompts in every purpose), and the Faceless purpose's poses and framings. Faceless is 18+ without the Intimacy step, so it never has nudity: anatomy only shows with nudity in the prompt, and the cover negatives are added in code (`negatives/`). A purpose's own `negative` in `prompt_modes.json` is added to its negative prompt.
- `frontend/src/lib/promptBuilder/filters/`: the Camera step's image filters (film, camera and print looks, full wording and tags) and the date stamp; a filter clashes with a colour grading and with sharp-focus realism details (`conflicts/`), so Surprise me drops those when it adds one.
- `frontend/src/lib/promptBuilder/spec/`: the JSON prompt (`PromptSpec`, versioned): the builder's choices grouped into sections, checked against the builder's options (`parseSpec`), and written as text for the model only when sent (`promptFromSpec`, through `buildPrompt`, so the purpose's rules and the age safeguard apply). The prompt box holds it when `promptFormat` is `json`, and its JSON | Text switch shows it or the text written from it (read-only); a typed prompt switched to JSON becomes the subject's description (`specFromText`); Generate sends the text and the JSON, and History keeps the JSON in `prompt_spec` (shape checked in `backend/prompt_spec.py`; both sides test `frontend/src/test/promptSpecExample.json`). Add a builder field to `FIELDS` there and to `prompt_spec.py`.
- `frontend/src/lib/promptBuilder/`: the prompt builder. Its option lists (`data/`) are generated from ComfyUI Photoreal Prompt Builder (see `THIRD_PARTY_NOTICES.md`); `build/` holds the state and checks; `resolveFacts/` turns the choices into facts (`facts/`) within what the mode allows (`rules/`, `choicesFor`), which `prose/` writes as a detailed paragraph in the mode's emphasis order (Z-Image, MOSS-Image) and `tags/` as a tag list with the mode's weights (WAI, Anime Desire), chosen by the model's `prompt_style`. A step the mode hides contributes nothing. `conflicts/` tags each option with what it uses (hands, body position, mouth, facing, legs, hair length, daylight, indoor, where a light can be) and finds clashes; `settle/` settles Random choices in order with `pickFitting` so they never clash, and Surprise me uses the same; clashes in the user's own choices show as warnings (`ClashWarnings`). Tag any new option there; `conflicts/index.test.ts` checks every option against Random.
- Uploaded face photos (`face_upload` on a character): such a character's images are kept safe for work, enforced in `render_and_save` in `main.py` with the rules in `safe_for_work.py` (sensitive prompts and start images refused, safe negatives added, a result the image check finds nudity in, or can't check, is discarded). Keep these rules on the server; the UI only hides the 18+ purposes and explains them.
- Sensitive images (blurred in lists, not when opened): `sensitive.py` marks a prompt by its words, and `nsfw_detector.py` (a small CPU image classifier, `models/nsfw-detector/`) checks each saved image; images saved before it loaded are checked by a background thread on start (`check_unchecked_images` in `main.py`). The check only ever adds the flag, and a flag set by hand (`set_sensitive`) is never changed. Tests turn the real check off in `tests/conftest.py`.
- `image_edits.py`: rotate, flip and crop recipes, applied with Pillow when an edited copy is saved (`POST /api/history/{id}/edits`); the original image is never changed.
- Scripted renders (`make render`, `frontend/scripts/renderSpecs.ts`, loaded through Vite by `scripts/render.mjs` because the app's code uses `import.meta.glob`): a list of JSON prompts, each optionally with name, model, size, steps, guidance, seed and character, rendered one at a time through the running web app and saved to `~/Pictures/z-image/`. Each request is built by `lib/renderRequest` (`renderRequest`, the same as Create's Generate) and `generateBody` in `api/`, so the text is written from the JSON with the purpose's rules and History keeps the JSON. Render images by script only this way, never by posting hand-written text.
- Chat (`chat_client.py`, `POST /api/chat`): turns a description into a prompt, streamed as plain text. `CHAT_PROVIDER` in `.env` picks Grok (`XAI_API_KEY`) or a local model through Ollama (`OLLAMA_MODEL`, `OLLAMA_URL`, `OLLAMA_KEEP_ALIVE`; Ollama's own `/api/chat`, since only it takes `keep_alive`, so the model unloads between chats). `ready_chat()` is the one check the catalog (`chat_available`, `chat_name`) and the endpoint share; a failure is a `ChatError` (a message for the user, a reason for the log). Each provider's system prompt is a constant in `system_prompts.py` (a small local model gets a short, direct one, or it copies a long prompt's steps into its answer). Pick uncensored builds of chat models. Every chat is saved (`chat_store.py`, tables `chat_conversations` and `chat_exchanges` in `history.db`): the question when it is sent, the answer when it ends (`saved_reply` in `main.py`: complete, failed or stopped, with the time to the first words and the total), the ids sent back in the `X-Chat-Conversation-Id` and `X-Chat-Exchange-Id` headers. Exchanges are only added, never changed: an edited question is a new exchange whose `parent_id` is the one before it. A new conversation is titled in a background thread (`title_conversation`, `system_prompts.TITLE`, best effort), and the image made right after an answer is linked to it (`chat_exchange_id` on generate, a `RunLink` like the A/B test's set, sent with that render only). Clearing History leaves chats alone; they will get their own controls.
- Decision model (Laya, `decision_model.py`): a small model (`convaiinnovations/laya`, English checkpoint, `models/laya/`) that answers typed questions about a text (`noul` yes/no, `choice`, `score`) instead of writing. It runs on the CPU in a child process (`laya_worker.py`, JSON lines over stdin and stdout, `ProcessLaya`), so unloading ends the process and gives all its memory back (inside the web app, the libraries and the allocator kept about 0.8 GB). One worker thread drives it (`LayaRunner`, one process at most, tasks queue), and only while there is work: it starts for a task and ends after it, or `DECISION_KEEP_ALIVE` seconds after the last; a caller can `preload()` so the load overlaps its own work (kept `PRELOAD_GRACE_SECONDS` for the task that follows). Every task gets a `trace_id`, in each of its log lines (logger `decision`) and in what it returns, a `DecisionError` included; the text is never logged. Tasks are constants in `decision_tasks.py` (questions plus the thresholds that decide in code, each read from `.env` through a `Threshold`, such as `DECISION_NUDITY_REFUSE_AT`, and listed in `.env.example`; `version` fingerprints the questions and the thresholds in use). The first, `NUDITY`, checks a chat question while adult content is locked (`adult_content.locked`, the same rule renders use): refused, or Laya failing (fails closed), ends the exchange unanswered (`refused` or `failed`), and each decision is saved in `decision_tasks` (`decision_store.py`, linked to `chat_exchanges`; errors are logged, not saved). `POST /api/decide` asks Laya any questions directly and saves nothing. `DECISION_MODEL=off` turns it off. Tests never load the real model (`no_real_laya` in `tests/conftest.py`).
- Logging (`log_setup.py`): both servers call `configure()` before `uvicorn.run(..., log_config=None)`, so every line, Uvicorn's included, has a time and level and goes to the terminal and a rotating `logs/<server>.log` (git-ignored), at `LOG_LEVEL` from `.env` (`INFO` by default). Each module logs through `logging.getLogger(...)`, never `print` (the command-line tools in `backend/tools/` excepted). Log what happened (loads, renders with their History id, downloads, refusals, deletes) with ids, settings and timings, never prompt text, character names, images, tokens or the unlock word; a test checks that a render's prompt stays out of the logs.
- `prompt_weights.py`: rewrites `(tag:1.3)` weights for Compel, which encodes SDXL prompts with weights and past 77 tokens (`sdxl_conditioning` in `model_server.py`).

- Adult content has two locks. `ADULT_CONTENT` in `.env` (`adult_content.py`, off by default) is enforced by the web app: off, the catalog leaves out adult purposes, models and add-ons (`adult` on `ModelSpec` and `AddonSpec`), History hides sensitive images everywhere (`check_shown`, `hide_sensitive`), and renders are kept safe with the uploaded-face rules (`safe_render_for`, `safe_for_work.py`). On, the browser adds its own (`lib/adultContent/`, `shared/adultContent/`): locked until the hidden word `ADULT_UNLOCK_WORD` is typed (checked by `POST /api/adult-content/word`), it works from `catalogFor(catalog, false)` and sends `safe_only` and `hide_sensitive`. Mark any new adult model or add-on `adult=True`.

## Translations

- The language comes from `APP_LANGUAGE` in `.env` (`en` default; `nl`, `it`, `fr`, `de`, `es`, `pt`), read by `backend/i18n.py` and sent to the UI in the catalog (`language`), which loads it before rendering (`LanguageGate` in `App/`).
- Frontend: `src/i18n/index.ts` (`t`, `tn` for plurals with `_one`/`_other` keys, `tOr` for text keyed by data such as purpose ids, `optionLabel` for prompt-builder options); messages in `src/locales/<code>/<namespace>.json`, English the source. Backend: `i18n.t()` with `backend/locales/<code>.json`.
- Look text up when it is shown, never at module load. Prompts sent to the models stay English: only labels are translated, option values never.
- Every language must have every key with the same placeholders (`src/i18n/locales.test.ts`, `backend/tests/test_i18n.py`); add a new text to all seven languages in the same change, and remove a key from all of them.

## Rules to keep

- Explicit, nudity and lingerie prompts in the prompt builder require "Who" and an adult age range, and are refused if any free text suggests a minor (`minorTermIn` in `build/`). A mode that shows the Intimacy step is always adult (`isAdultMode` in `modes/`), so editing `prompt_modes.json` can never switch these checks off. Keep this when changing the builder.
- Only one model is loaded at a time; switching models unloads the previous one first.
- Icons come from `lucide-react`, never hand-drawn SVGs or text symbols; their size and line weight are set once (`.lucide` in `index.css`). A button that shows only an icon uses `IconButton`, which gives it its accessible name and a tooltip (with its keyboard shortcut, if it has one).
- The same purpose uses the same control everywhere it is edited: one shared component for the sidebar, the prompt builder and the character dialog (the look sliders are one `LookSliderField`). When one place changes, change them all; and hide a sidebar control for a prompt from the prompt builder when the builder already sets it.
- Every dialog uses `Modal`. A key a dialog handles (Escape, the image viewer's keys) acts only on the dialog on top (`shared/ui/topDialog`), so a dialog opened over another closes alone. History, Characters, the prompt builder and the A/B test dialog load the first time they are opened (`lazy`, with a placeholder meanwhile); keep the first screen, Create, light.
- Every dialog uses `Modal`: a header with the title and a close button, then the content, then its buttons passed as `actions`, under a divider, secondary action first and main action last. They are centred on their own, or on the right when a note (`actionsNote`) sits beside them on the left. A dialog with two columns (such as the image view) puts its actions at the bottom of the details column instead, under a divider, aligned right.
- Phones come first in the layout. Below 640px (`sm`) the views are a bar at the bottom, every `Modal` is a bottom sheet (`md`) or fills the screen (larger sizes) with full-width buttons, and fields use 16px text so iOS does not zoom in. Below 1024px (`lg`) Create shows Settings or Result, one at a time (`PaneSwitch`). Touch screens get 44px targets and no hover-only controls through `pointer-coarse:` (`IconButton`, `tabClass`, `secondaryButtonClass`, `Checkbox`); keep new controls the same, and keep clear of the notch and home bar with `env(safe-area-inset-*)`.
- Device is Apple MPS/MLX; the code assumes Apple Silicon and does not run usefully in Docker or on CPU.
