PLAN: Smaller images in history.db
Date: 2026-10-29 12:09
Status: draft, waiting for review

GOAL
Make history.db smaller by storing each new image as lossless WebP instead of PNG,
with no change to what the images look like, and no schema change (no new columns).
Existing PNG rows keep working as they are; shrinking them is an optional, separate step.

WHY LOSSLESS ONLY
Variations, the face lock, edits and the image check all start from the stored image,
so it must stay pixel-identical to what the model made. Lossy WebP/AVIF and JPEG XL are
out of scope (see OUT OF SCOPE).

CURRENT STATE (checked in the code)
- history_store.py: images.image_data BLOB holds the PNG; add() inserts NewImage.png.
- history_store.image_png(id) feeds: the image check (main.py image_is_nsfw), variations
  (main.py, source image), the face lock (main.py, character face), edits (save_edit),
  the palette, the History export zip, and GET /api/history/{id}/image.
- GET /api/history/{id}/image always answers media_type="image/png".
- Download links in ResultPanel.tsx and HistoryViewer.tsx use that URL with a ".png"
  file name.
- The history export writes each image as "<name>.png" (history_export.py).
- All readers except the route and the export decode with Pillow, which opens any format.
- history_store.compact() runs VACUUM after deleting images. No WAL or auto_vacuum.

DESIGN
No column. A stored image is told apart by its first bytes: PNG starts with
89 50 4E 47, WebP with "RIFF....WEBP". Rows written before this change are PNG and
need no migration to keep working.

New file backend/image_codec.py (small, pure, no database)
- encode_for_storage(png: bytes) -> bytes
  - Open with Pillow. Drop the alpha channel only when it is fully opaque; keep it
    otherwise. Drop metadata chunks (prompt and settings already live in columns).
  - Save as lossless WebP (method chosen by the benchmark, step 0).
  - Safety net, always: decode the result and compare pixels with the source. If they
    differ, or the WebP is not smaller than the PNG, return the original PNG bytes.
    So a stored copy is never different from, or bigger than, what the model made.
- to_png(stored: bytes) -> bytes: returns PNG bytes; a PNG goes through unchanged.
- media_type(stored: bytes) -> str: "image/png" or "image/webp" by header.

history_store.py
- add(): store encode_for_storage(image.png). NewImage.png keeps its name (it is what
  the caller hands over); only the stored bytes change.
- image_png(id): keeps its name and meaning, now converts with to_png when the row is
  WebP. Every existing consumer (image check, variations, face lock, edits, palette)
  is untouched and always gets PNG.
- New stored_image(id) -> bytes | None: the raw stored bytes, for the image route.
- images(filters): keeps yielding PNG (converted), so the export zip is unchanged
  and its files stay real PNGs.

main.py
- GET /api/history/{id}/image: sends stored_image() with media_type from the header, so
  the browser gets WebP directly with no conversion. ?thumb=true stays as it is.
- Downloads: add GET /api/history/{id}/download (PNG via image_png, Content-Disposition
  attachment, name z-image-<id>-<seed>.png). Without it, a ".png" download of a
  WebP body would be misnamed.

frontend/src/
- api.ts: downloadUrl(id). ResultPanel.tsx and HistoryViewer.tsx point their download
  links at it instead of imageUrl(). Displaying images keeps using imageUrl().

Optional backfill (separate step, run by hand, not at startup)
- backend/tools/recompress_history.py, run with uv run python backend/tools/recompress_history.py
  - --dry-run: reports how many PNG rows, current size, estimated saving, no writes.
  - Copies history.db to history.db.bak first (SQLite backup API, safe while in use),
    unless --no-backup is passed.
  - Per row, in its own transaction: encode, verify pixels, replace image_data.
    Rows already WebP are skipped, so it is safe to stop and run again. --limit N.
  - Runs compact() at the end, since the file only shrinks after VACUUM.
- Not automatic on purpose: rewriting a user's whole database should be something
  they start, after a backup, not a side effect of updating.

Database settings (separate small step, after the above has settled)
- journal_mode=WAL (readers do not block the model server's saves) and
  auto_vacuum=INCREMENTAL (deleted images return space without a full VACUUM).
- auto_vacuum only applies to a new database or after VACUUM, so it takes effect
  for existing databases after the backfill's compact().

MIXED VERSIONS
An older build opening a database with WebP rows: Pillow-based code reads them fine;
the old image route labels them image/png, which browsers still display (they sniff the
content), but a ".png" download would hold WebP bytes. So: ship the new version
everywhere before running the backfill, and do not run it if an older copy is in use.

ROLLBACK
- New saves: revert the change; WebP rows stay readable by the new reader code, so keep
  the reader part even if the encoder is turned off.
- Backfill: history.db.bak is the undo. Since the conversion is lossless, a row can
  also be converted back to PNG exactly (to_png) until the backup is deleted.

STEP 0: MEASURE BEFORE BUILDING (decides the defaults)
Take about 20 real images (all models, mixed sizes, a couple of edited copies). Compare
PNG as stored, PNG optimize=True, lossless WebP at methods 4 and 6, for size and
encode time at the largest preset. Go ahead only if lossless WebP saves at least about
15% and encoding stays under about 2 seconds at the largest size; pick the method
from the numbers. If the saving is smaller, stop at PNG optimize=True (still no schema
change) or do nothing.

TESTS
- Backend (uv run pytest), fake images, no models needed:
  - image_codec: round trip is pixel-identical for RGB, RGBA with real transparency,
    and a palette image; fully opaque RGBA becomes RGB; metadata is dropped; when the
    WebP would be bigger the original PNG bytes come back; header detection for both
    formats; to_png of a PNG is the same bytes.
  - history_store: add() then image_png() returns an identical PNG; a row written as
    plain PNG (old format) still reads; stored_image() returns the raw bytes.
  - Routes: /image answers image/webp for a new image and image/png for an old row;
    /download answers a real PNG with the right file name; the export zip holds PNGs
    that open with Pillow.
  - A variation, an edit and a face lock started from a WebP-stored image work.
  - Backfill script: dry run writes nothing; a second run changes nothing; a row whose
    verification fails is left as it was; the backup file is created.
- Frontend (npm test, npx tsc -b, npx oxlint src): the download links use downloadUrl.
- Whole set: make check.

DOCS
- CLAUDE.md "Code layout": history_store.py line (images are stored as PNG or lossless
  WebP, told apart by their header); add image_codec.py and the backfill tool.
- README.md or docs/usage.md: one note on the optional backfill and the backup it makes.
- No new user-facing text, so no translation keys.

DEFAULTS CHOSEN (change on review if wanted)
1. Lossless WebP only; PNG is kept whenever WebP is not smaller or not identical.
2. No schema change: the format is read from the bytes.
3. Existing images are only re-encoded by the manual backfill, never automatically.
4. Downloads and the export zip stay PNG.
5. Thumbnails are unchanged (still made on request).
6. character_store's uploaded face photo stays PNG (small, rarely read).

OUT OF SCOPE (candidates for later, each worth measuring first)
- Lossy WebP/AVIF "archive" copies for old images, JPEG XL.
- Storing thumbnails at save time in their own table, and moving image bytes into a
  separate table so History queries never touch them.
- Image files on disk instead of BLOBs (only if the database reaches tens of GB).
- Compressing the BLOB again (PNG and WebP are already compressed; no gain).

OPEN QUESTIONS
- How long does lossless WebP take at the largest preset on this Mac? If it is more than
  a second or two, encode off the request thread or pick a faster method.
- Does anything outside this repo read history.db directly (scripts, other tools)? They
  would see WebP rows and need to cope; the answer decides whether step 5 is safe.
